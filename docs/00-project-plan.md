## 1. 项目概述

### 1.1 一句话定位

> 把散落在问卷、访谈记录、应用商店评论、群聊里的海量用户反馈，通过 AI 管线自动聚类、提炼洞察、生成 PRD 草稿与任务拆解，并由 PM 人工审核采纳——一个"用户声音 → 产品决策"的工作台。

### 1.2 项目背景与动机

- **求职目标**：AI 产品经理 / 技术 PM 岗位。

- **现有项目盘点结论**：GitHub 上 5 个项目（RAG-Forge、gaokao-tianzhiyuan.agent、tactical-grid、ppt-master-dps、windows-deep-cleaner）全部在证明"我能造东西"（工程师叙事），缺少"我能发现问题、定义方案、组织资源、用数据验证"的产品叙事。

- **本项目的使命**：补齐产品叙事这一翼，与 RAG-Forge 的技术深度形成"懂技术 + 懂产品"的完整 PM 画像。

### 1.3 目标岗位画像与能力矩阵

| 目标岗位核心能力         | 本项目中的证明方式                            |
| ---------------- | ------------------------------------ |
| 用户调研与需求洞察        | 3\~5 位 PM 访谈 → 痛点排序 → PRD（docs/ 可查证） |
| 产品定义与范围控制        | MoSCoW 划分 MVP 边界 + 迭代日志中的砍功能决策记录     |
| AI 能力边界认知        | PRD 生成后强制人工审核环节的设计与论述                |
| 数据驱动验证           | 北极星指标（PRD 采纳率）+ 效率对比实验               |
| 技术理解力（技术 PM 加分项） | 亲自实现 embedding + 聚类 + LLM 生成管线       |
| 项目管理             | 14 天排期、风险清单、决策记录机制                   |

### 1.4 与现有项目的组合策略（面试组合拳）

| 项目                       | 在组合中的角色                             |
| ------------------------ | ----------------------------------- |
| RAG-Forge                | 技术深度："我懂 AI 检索与评测的底层原理"             |

## 2. 用户调研计划

### 2.1 目标用户画像

- **主画像**：1~~5 年经验的 to C / to B 产品经理，每周需要处理 100+ 条多渠道用户反馈，手工整理耗时 2~~6 小时。

- **次画像**：独立开发者 / 小团队负责人（一人分饰 PM + 开发）。

### 2.2 调研方法与访谈提纲

- **对象**：3\~5 位 PM（朋友、产品社群、脉脉/即刻）。

- **形式**：30 分钟一对一访谈（线上即可，全程记录）。

- **提纲**：

  1. 你现在从哪些渠道收集用户反馈？各自占比？
  2. 上一次整理反馈是什么时候？花了多久？具体步骤是什么？
  3. 整理过程中最烦躁 / 最耗时的环节是哪一步？
  4. 你用过哪些工具（问卷星、飞书多维表格、Dovetail、Excel）？为什么弃用或继续用？
  5. 如果 AI 能帮你做其中一步，你最希望是哪一步？最不放心 AI 做哪一步？
  6. 产出物最终给谁看？（老板 / 研发 / 自己）格式要求是什么？

- **产出物**：`docs/01-user-research.md`，包含访谈纪要、痛点频次排序、用户旅程图（现状版）、关键引语（脱敏）。

### 2.3 调研成功标准

- 至少 3 位有效访谈；

- 痛点排序中"归类去重耗时"或"从反馈到需求文档的转化"位列 Top 3（否则需回到方案选型阶段重评，此为关键决策点）。

## 4. 产品需求定义（PRD 摘要）

### 4.1 问题定义

**用户问题陈述**：PM 每周花费数小时将非结构化用户反馈（评论/问卷/访谈）整理为结构化需求输入，过程中大量时间耗在归类、去重、翻译"用户语言 → 产品语言"上，且整理结果难以追溯原始依据。

**我们解决**：其中的**归类、去重、初步翻译、文档草稿化**四个环节（人工保留：判断优先级、审核采纳、最终决策）。

**我们不解决**（边界声明，写入 README）：反馈的自动采集（爬虫）、团队协作、需求优先级的最终决策。

### 4.2 产品目标与北极星指标

- **产品目标**：500 条原始反馈 → 结构化需求洞察 + PRD 草稿，端到端 ≤ 10 分钟（人工基线约 3 小时）。

- **北极星指标**：**PRD 采纳率** = 生成草稿中被保留（含轻改）的段落比例。目标 ≥ 60%。

- **护栏指标**：单次全流程 API 成本 ≤ ¥1；处理时长 ≤ 10 分钟。

### 4.3 MVP 边界（MoSCoW）

**Must（P0，两周内必须交付）**

| #  | 功能       | 说明                                        |
| -- | -------- | ----------------------------------------- |
| M1 | 数据导入     | CSV/Excel 上传 + 文本框粘贴 + 内置演示数据集一键加载        |
| M2 | 清洗去重     | 去空值、去完全重复、超长截断、简单脱敏                       |
| M3 | AI 聚类分析  | embedding → 降维 → 聚类 → LLM 主题命名            |
| M4 | 洞察报告     | 每个主题：代表原文摘录（可追溯）、频次、情感倾向、AI 提炼的痛点描述       |
| M5 | PRD 草稿生成 | 按模板输出：背景 / 用户故事 / 需求列表（优先级建议）/ 风险         |
| M6 | 人工审核     | 逐段采纳 / 编辑 / 拒绝，拒绝需选原因（幻觉/跑题/表述差）——此数据反哺指标 |
| M7 | 导出       | Markdown 文件下载                             |

**Should（P1，时间富余才做）**

| #  | 功能         | 说明                 |
| -- | ---------- | ------------------ |
| S1 | 频次/情感可视化图表 | 柱状图 + 词云           |
| S2 | 任务拆解       | PRD → 用户故事卡（含验收标准） |
| S3 | 处理历史列表     | 本地会话级保存，可回看        |

**Could（P2，仅记录不做）**：飞书文档导出、多语言反馈自动翻译、自定义聚类粒度参数暴露到 UI。

**Won't（明确不做，写入 README 控制预期）**：多用户/账号系统、云端持久化数据库、实时协作、自动采集爬虫、移动端适配。

### 4.4 用户故事（核心 5 条）

1. 作为 PM，我想上传一份导出的评论 CSV，以便不用手工粘贴拆分。
2. 作为 PM，我想让系统自动把 500 条评论归成若干主题，以便我不用逐条读。
3. 作为 PM，我想看到每个主题下的原始反馈摘录，以便验证 AI 归类是否可信。
4. 作为 PM，我想在 AI 生成的 PRD 草稿上直接编辑并采纳，以便保留最终决策权。
5. 作为 PM，我想导出成 Markdown 给研发，以便直接进入排期讨论。

### 4.5 核心用户流程

```
导入数据 → (自动)清洗 → (自动)聚类+命名 → 查看/校对主题
  → (自动)生成洞察报告 → (自动)生成 PRD 草稿
  → 人工审核(采纳/编辑/拒绝) → 导出 Markdown
```

关键交互原则：**每一步 AI 产出都必须能回溯到原始数据**（点开主题看原文；PRD 每个需求点标注来源主题 ID）。

### 4.6 功能详细拆分（含验收标准）

#### M1 数据导入

- 输入：CSV（≤ 5000 行）/ Excel / 粘贴文本（每行一条）/ 演示数据集。

- 处理：列映射（自动猜测文本列，允许手动指定）；编码自动检测（UTF-8/GBK，中文场景高频坑）。

- 验收标准：演示数据集一键加载 ≤ 3 秒；GBK 编码 CSV 正确解析；无文本列时给出明确报错。

#### M2 清洗去重

- 处理：去空值 → 完全重复合并（保留计数）→ 长度 >500 字截断 → 正则脱敏（手机号/邮箱）。

- 输出：清洗报告（原始 N 条 → 有效 M 条，各步骤丢弃数）。

- 验收标准：注入的重复样本被合并且计数正确；清洗报告数字自洽。

#### M3 AI 聚类分析（技术核心）

- 管线：embedding（全部反馈）→ UMAP 降维 → HDBSCAN 聚类 → 每簇抽样 10\~20 条 → LLM 命名主题 + 一句话描述。

- 降级方案：HDBSCAN 不可用或簇质量差时，回退 KMeans（K 由轮廓系数自动选择）。

- 噪声点处理：HDBSCAN 的 -1 簇标记为"未归类"，不强行分配。

- 验收标准：演示数据集聚类后 ≥ 80% 的簇主题命名人工评为"合理"（自评 + 1 位 PM 朋友盲评）；单簇原文摘录可展开查看。

#### M4 洞察报告

- 每主题字段：主题名 / 描述 / 反馈条数与占比 / 情感分布（正/中/负）/ 代表性原文 3~~5 条 / AI 提炼痛点 1~~2 句。

- 情感分析：LLM 批量分类（每批 20 条，要求输出 JSON）。

- 验收标准：主题按条数降序排列；原文摘录一键定位到导入的原始行。

#### M5 PRD 草稿生成

- 输入：主题洞察 + 用户在 UI 上勾选"纳入 PRD"的主题。

- 模板结构：背景与目标 / 用户画像摘要 / 需求列表（每条：描述、用户故事、优先级建议、来源主题）/ 风险与开放问题。

- 验收标准：输出为结构化 Markdown；每条需求带来源主题 ID 可回溯；生成耗时 ≤ 60 秒。

#### M6 人工审核（产品灵魂）

- 交互：PRD 分段展示，每段三个操作：采纳（原文保留）/ 编辑（进入编辑框）/ 拒绝（必选原因：幻觉 / 跑题 / 表述差 / 重复）。

- 数据：审核操作全部记录（为指标页提供数据源）。

- 验收标准：拒绝必须选原因才能继续；采纳率实时计算显示。

#### M7 导出

- 导出内容：PRD（含审核结果）+ 洞察报告附录 + 数据处理元信息（模型名、处理时间、清洗统计）。

- 验收标准：导出的 Markdown 在 Typora/VS Code 渲染无格式错误；元信息完整（体现可复现性）。

### 4.7 非功能需求

| 维度  | 要求                                              |
| --- | ----------------------------------------------- |
| 性能  | 500 条反馈端到端 ≤ 10 分钟（含 LLM 调用）                    |
| 成本  | 单次全流程 API 成本 ≤ ¥1                               |
| 隐私  | MVP 本地运行模式（数据不出本机，仅调用模型 API）；README 明确声明        |
| 可复现 | 相同输入 + 固定 seed 的聚类结果一致；LLM 部分记录模型版本             |
| 容错  | LLM 调用失败自动重试 2 次（指数退避），仍失败则该步骤标记失败并允许重跑，不阻塞其他步骤 |
| 兼容  | Chrome/Edge 最新版；桌面优先，不做移动端                      |

### 4.8 人工审核环节设计说明（面试高频考点，务必在 README 论述）

设计立场：AI 负责"归纳与初稿"，人负责"判断与决策"。三条论据：

1. 幻觉风险：LLM 可能编造用户没说过的需求 → 拒绝原因里专门有"幻觉"选项并统计，形成可信度数据；
2. 优先级判断需要业务上下文（ROI、战略），AI 不具备 → PRD 中 AI 只给"建议优先级"并标注置信度；
3. 采纳率数据让"AI 好不好用"从主观感受变成可量化指标 → 这本身就是 AI 产品方法论。

## 5. 指标与验证方案

### 5.1 指标体系

| 层级  | 指标          | 定义                  | 目标             | 采集方式           |
| --- | ----------- | ------------------- | -------------- | -------------- |
| 北极星 | PRD 采纳率     | (采纳 + 轻改段落) / 总生成段落 | ≥ 60%          | 审核操作日志         |
| 效率  | 端到端处理时长     | 导入完成 → 导出完成         | ≤ 10 分钟（500 条） | 前后端时间戳         |
| 效率  | 人工基线对比      | 同任务人工整理耗时（访谈 + 自测）  | 提升 ≥ 10 倍      | 访谈记录 + 自测计时    |
| 质量  | 主题命名合理性     | 盲评 1\~5 分           | 均分 ≥ 3.5       | 自评 + 1 位 PM 盲评 |
| 质量  | 拒绝原因分布      | 幻觉占比                | ≤ 15%          | 审核日志           |
| 成本  | 单次流程 API 费用 | 全管线 token 折算        | ≤ ¥1           | 用量统计页          |

### 5.2 验证实验设计

- **被试**：本人 + 2\~3 位 PM 朋友。

- **任务**：同一份 500 条演示数据，各自走完整流程并导出 PRD。

- **测量**：任务耗时、采纳率、主观可用性评分（1\~5）、盲评（将 AI 辅助产出与某位 PM 纯手工产出混洗后评分）。

- **产出**：`docs/03-metrics.md` 中的实验结果章节（诚实呈现，即使指标未达标——"发现聚类在 XX 类反馈上表现差"本身就是 PM 素养的证明）。

## 6. 技术方案

### 6.1 技术选型及理由

| 层         | 选型                                                                   | 理由                               |
| --------- | -------------------------------------------------------------------- | -------------------------------- |
| 后端        | Python 3.11+ / FastAPI                                               | 与 RAG-Forge 技术栈一致，形成技能复用叙事；异步支持好 |
| 前端        | React 18 + Vite + TypeScript + 自研 tokens 设计系统（无 UI 库）          | 用户有 TS 项目经验；Vite 轻量；自研设计系统统一风格且零依赖（对接实际落地） |
| Embedding | 本地 BGE-small-zh（sentence-transformers，主）+ TF-IDF/哈希（降级）；embedding API 实测无权限 | 离线可用、中文语义质量高；订阅型 key 无向量能力 → 本地为主（见 v0.2） |
| 降维        | UMAP（n≥50 触发，否则直连聚类）                                             | 小样本跳过降维避免失真                        |
| 聚类        | HDBSCAN（主）/ KMeans（降级）/ 单条与全重复走 quick 路径                              | 无需预设 K、对噪声鲁棒；多级降级保证可用            |
| LLM       | OpenAI 兼容接口，抽象 Provider 层（火山方舟 glm-5-3-flash 实测；Coding Plan 端点 /api/plan/v3） | 国产模型成本低；Provider + Fallback 熔断展示工程素养 |
| 存储        | 审核日志 JSONL 追加文件（无 schema、零锁）+ localStorage 会话交接                     | MVP 单机够用；升级 DB 时 JSONL 可直接迁移（见 v0.6） |
| 部署        | Docker Compose 一键本地运行；演示视频 + 在线 Demo（Railway/Render 免费 tier，可选）      | 本地优先保隐私；在线 Demo 方便面试官 30 秒体验     |

### 6.2 系统架构

```
frontend (React SPA)
    │ REST / SSE（进度推送）
backend (FastAPI)
    ├─ api/          路由层：upload / pipeline / review / export
    ├─ services/
    │   ├─ ingest      导入与列映射
    │   ├─ clean       清洗去重脱敏
    │   ├─ cluster     embedding → UMAP → HDBSCAN
    │   ├─ insight     主题命名、情感分析、痛点提炼
    │   ├─ prd_gen     PRD 草稿生成（结构化输出）
    │   └─ export      Markdown 渲染导出
    ├─ prompts/        全部 Prompt 集中管理（版本化，面试展示点）
    ├─ core/           LLM Provider 抽象、配置、重试
    └─ models/         SQLite ORM（Feedback, Topic, ReviewLog, Run）
外部依赖：Embedding API、LLM API
```

SSE（Server-Sent Events）推送管线各阶段进度——处理 500 条需要几分钟，必须有进度反馈，否则体验崩坏。

### 6.3 AI 管线详细设计

| 阶段        | 输入 → 输出                     | 模型调用策略                   |
| --------- | --------------------------- | ------------------------ |
| embedding | 清洗后反馈 → 向量矩阵                | 批量（batch=100），缓存向量避免重复计算 |
| 聚类        | 向量 → 簇标签                    | 纯本地计算，无 API              |
| 主题命名      | 每簇抽样 10\~20 条原文 → 主题名 + 描述  | 每簇 1 次调用，温度 0.2，JSON 输出  |
| 情感分析      | 每簇反馈 → 正/中/负标签              | 每批 20 条合并调用，温度 0         |
| 痛点提炼      | 簇原文 + 主题名 → 痛点句             | 与主题命名合并为一次调用以省成本         |
| PRD 生成    | 勾选主题的洞察 JSON → PRD Markdown | 单次调用（长上下文），温度 0.3        |

### 6.4 Prompt 设计原则（集中存放 `backend/prompts/`）

1. 全部 Prompt 独立成文件、版本化管理——面试时可展示 Prompt 迭代过程；
2. 结构化输出强制 JSON Schema，解析失败自动重试并降级；
3. 主题命名 Prompt 中明确要求"基于原文用词，禁止发明用户未提及的概念"（对抗幻觉）；
4. 每个 Prompt 附带 3\~5 条 few-shot 样例（从演示数据中挑选）。

### 6.5 数据与存储方案

- 表设计：`feedback(id, run_id, raw_text, clean_text, cluster_id, sentiment)`；`topic(id, run_id, name, description, count, insight)`；`review_log(id, prd_id, section, action, reason, edited_text, created_at)`；`run(id, created_at, model_config, stats_json)`。

- 一切以 `run` 为单位隔离，支持多次实验对比（也服务于指标验证）。

### 6.6 成本估算（500 条反馈，单次全流程）

| 调用        | 次数     | 估算 token    | 费用（GLM/DeepSeek 档）   |
| --------- | ------ | ----------- | -------------------- |
| embedding | 500 条  | \~5 万 token | \~¥0.02              |
| 主题命名+痛点   | \~10 簇 | \~3 万 token | \~¥0.1               |
| 情感分析      | \~25 批 | \~4 万 token | \~¥0.1               |
| PRD 生成    | 1 次    | \~1 万 token | \~¥0.05              |
| **合计**    | <br /> | <br />      | **\~¥0.3，满足 ≤¥1 目标** |

### 6.7 部署方案

- 主路径：`docker-compose up` 一键启动前后端 + SQLite，README 附 3 行快速开始；

- 演示路径：录制 2 分钟端到端演示视频（Loom/B站），README 嵌入——面试官 30 秒无门槛看懂价值；

| 为什么用聚类不用分类？      | 反馈主题事先未知且持续变化，无标注数据；聚类是无监督发现，分类需要先有人定义类目——这本身是 PM 对问题本质的判断 |

| 成本怎么控制？          | 批量调用、向量缓存、Provider 抽象切换国产模型；实测 ¥0.3/次                      |
| 如果重做会改什么？        | 迭代日志里的真实教训（做完后回填，比编的更有说服力）                                 |
| 和 RAG-Forge 的关系？ | 组合叙事：一个管知识输入的可信，一个管需求输入的可信，共享"可评测、可审核"的工程价值观               |
