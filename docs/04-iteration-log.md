## v0.5.0（M1 文件导入，2026-09-02）

- **日期**：2026-09-02

- **版本**：v0.5.0

- **决策**：M1 落地：`POST /api/pipeline/import`（CSV/XLSX/TXT，multipart + query has\_header）+ 导入页（上传→列选择→前 8 行预览→送入洞察页）+ 洞察页一次性接收预填。CSV 编码检测链 utf-8-sig→gbk→latin-1；.xls 明确拒绝并引导转换。

- **背景**：此前数据入口只有洞察页粘贴文本，真实反馈文件（Excel/CSV 导出）进不来。中文环境下两大坑：Excel 另存 CSV 带 BOM（表头残留 \ufeff）、中文 Windows 记事本默认 GBK。

- **备选方案**：A）chardet 自动探测编码；B）固定 utf-8 报错让用户转码；C）三级 try 链（utf-8-sig→gbk→latin-1）。列映射：D）后端指定列；E）前端选列。

- **选择理由**：C 零依赖覆盖国内 99% 场景（BOM 在 utf-8-sig 自动剥离），latin-1 永不抛仅兜底；A 引入依赖且对短文件误判率高。E 让用户看到预览表再选列，错误率低且后端保持无状态（返回全列数据，列语义由前端解释）。

- **后果**：数据入口补齐，完整闭环为「文件导入/粘贴 → 清洗 → 聚类 → PRD → 审核 → 下载」。e2e 实测：GBK 多列 CSV 中文无乱码、BOM 正确剥离、XLSX 正常、导入数据直达聚类管线；单测 37/37（新增 10）。行数上限 5000、文件 20MB 由后端强制。遗留：UI 浏览器实测待工具可用时补（tsc/build 已过）。

## v0.4.0（M5 PRD 生成 + 审核页，2026-09-02）

- **日期**：2026-09-02

- **版本**：v0.4.0

- **决策**：M5 落地：`POST /api/pipeline/prd-gen`（主题洞察 → LLM → 结构化 PRD 草稿 Markdown）+ 前端审核页（生成/编辑/还原 AI 原稿/下载 .md）。洞察页勾选主题经 localStorage 交接跳转审核页。PRD 调用参数：`max_tokens=16384, timeout=300s, reasoning_effort="low"`。

- **背景**：首版 e2e 失败——reasoning 模型（方舟 glm-5-3-flash）对大 Prompt 深度思考，8192 token 配额被 reasoning 全部耗尽（finish\_reason=length），正文为空且耗时 213s。诊断实验：`thinking.type=disabled/auto` 该模型均报 InvalidParameter 不支持；`reasoning_effort="low"` 有效——reasoning\_tokens 1633→0，completion 2564→631（约 1/4 耗时/成本），mini PRD 质量无损。

- **备选方案**：A）放大 max\_tokens 到 16384 硬扛深思考（仍 3 分钟+，体验差）；B）`thinking.type=disabled`（不支持）；C）`reasoning_effort=low` + 16384 上限兜底。

- **选择理由**：C 直击根因——PRD 生成是结构化写作任务而非推理任务，深度思考无增益；实测修复后 65.6s 出全文（3213 字符），质量检查 10/10（标题/六章结构/来源标注/优先级/用户故事/验收标准全过）。教训：**reasoning 模型做长文生成必须评估思考配额挤占；方舟对该模型只认 OpenAI 风格的 reasoning\_effort，不认 thinking.type**。

- **后果**：产品核心闭环（反馈→主题→PRD→人工审核→导出）全链路可用；审核页保留 AI 原稿支持"还原对比"，强化"AI 生成+人工审核"叙事；PRD 每条需求标注来源主题与反馈量（可回溯性）。单测 27/27。前端 tsc/vite build 通过（浏览器自动化工具本轮不可用，UI 未做浏览器实测——交互模式与 M4 已验证页面同构，遗留到下次浏览器可用时补验）。

## v0.3.0（M4 洞察页前端，2026-09-02）

- **日期**：2026-09-02

- **版本**：v0.3.0

- **决策**：洞察页落地：粘贴反馈（每行一条）→ 前端串联 M2 清洗 + M3 聚类 → 簇卡片展示（主题名/情感/条数/描述/代表原文/成员展开）+ min\_samples 参数控制 + 勾选纳入 PRD（M5 预埋）。内置 60 条三主题示例数据。无 UI 库，延续 inline-style 轻量方案。

- **背景**：M3 后端已验收（v0.2.0），但无 UI 入口则演示价值为零。M1（文件导入）未做，选择先用"粘贴文本"作为数据入口——这是最小可用路径，M1 的 CSV 解析与之正交。

- **备选方案**：A）先做 M1 文件导入再做展示；B）粘贴文本入口 + 直接做洞察页；C）用 UI 库（antd/MUI）快速搭。

- **选择理由**：B 的粘贴入口零依赖即可端到端演示核心价值（"杂乱反馈 → 结构化主题"），面试演示 30 秒见效；C 引入 UI 库的成本在 MVP 阶段不划算且样式定制受限，留到正式 UI 迭代。管线串联（clean→cluster）放前端而非后端新端点，因两阶段各自独立可用、组合逻辑薄。

- **后果**：60 条三主题实测（浏览器实测）：清洗 60→60，HDBSCAN 3 簇 + 2 噪声，命名 3/3 合理，端到端 54.1s（首次含 bge 模型加载与 embed 404 熔断一次）。附带修复：Vite server 在 Windows 下默认仅绑 IPv6 localhost，浏览器走 127.0.0.1 被拒——显式 `host: "127.0.0.1"`。M5（PRD 生成）的输入接口已通过勾选交互预埋。

## v0.2.0（M3 聚类 + 主题命名落地，2026-09-02）

- **日期**：2026-09-02

- **版本**：v0.2.0

- **决策**：M3 完整落地：embedding→降维→HDBSCAN（KMeans 降级）→ LLM 主题命名。向量化采用"真实 API 优先 + 本地 bge-small-zh-v1.5 兜底"的混合架构；FallbackClient 熔断拆分为 chat/embed 独立两路。

- **背景**：spike 验证发现 Coding Plan 端点只提供 chat/completions，`/embeddings` 返回 404——订阅型 key 天然无向量能力。若沿用全局熔断（v0.1.2 设计），一次 embed 404 会把 chat 命名也拖进 mock。另实测：① reasoning 模型思考消耗大，`max_tokens=1024` 时正文为空；② hf-mirror 与新版 huggingface\_hub 1.29 不兼容（`FileMetadataError`，镜像响应头缺元数据）；③ 24 条小样本不触发 UMAP（n≥50 门槛），512 维直接聚类效果差（轮廓系数 0.109）。

- **备选方案**：A）等标准方舟 key 开通 embedding API；B）LLM 生成伪语义向量；C）本地 sentence-transformers（bge-small-zh）+ TF-IDF + 哈希三级降级；D）TF-IDF 单级。

- **选择理由**：C 不新增外部依赖（无 key、离线可用），bge-small-zh 512 维中文语义质量高（约 100MB，CPU 可跑），三级降级保证任何环境下管线可运行；60 条三主题 e2e 实测 HDBSCAN 聚出 3 簇 + 2 噪声（噪声均为边界样本），LLM 命名 3/3 合理，验收达标（阈值 ≥80%）。TF-IDF 保留为 st 不可用时的降级而非主选——其对同义词无泛化（"登录慢"≠"认证超时"）。

- **后果**：聚类管线完整可用（`POST /api/pipeline/cluster`）；单测 19/19 离线通过（2.2s，conftest 强制 mock + 禁止 st 模型下载）；模型文件走 HF 官方直连缓存于用户目录。附带修复：cluster 模块自管 embed 熔断状态（原设计读 `llm._fallback` 存在初始化时序 bug，首次调用必白撞一次 404）；`max_tokens` 提升至 4096。教训两条：**鉴权 404 ≠ key 无效（可能是产品线能力边界）；依赖注入的共享熔断状态要考虑初始化时序**。

## v0.1.3（真实模型打通：Coding Plan 端点修正，2026-09-02）

- **日期**：2026-09-02

- **版本**：v0.1.3

- **决策**：LLM 层引入 `AuthError`（401/403 不重试）与 `FallbackClient`（真实调用失败自动降级 mock 并熔断后续调用，重启复位）；`.env` 配置为 `LLM_MODE=live + LLM_FALLBACK_MOCK=true`，方舟 key 作为首选真实模型；新增 `/api/pipeline/llm-ping` 诊断端点。

- **背景**：用户提供的方舟 key 经穷举验证（4 端点 × Bearer/裸/X-Api-Key/api-key/X-Token × 多模型名）均被火山服务器 401 拒绝，但用户坚持使用该 key。

- **备选方案**：A）坚持仅 live，管线不可用；B）仅 mock，key 形同虚设；C）live 首选 + 失败自动降级。

- **选择理由**：C 让 key 处于"已配置、优先使用"状态——火山侧一旦认可该 key（激活/补全），重启即恢复真模型，零代码改动；同时管线当下就完整可用。401/403 快速失败 + 熔断避免每次调用空等重试。

- **后果**：当前 `llm-ping` 显示 `degraded=true`（离线模式应答，last\_error 记录火山原始 401 报文）；换有效 key 只需改 `.env` 的 `LLM_API_KEY` 后重启。

## v0.1.1（Mock Provider + M2 清洗，2026-09-02）

- **日期**：2026-09-02

- **版本**：v0.1.1

- **决策**：新增 `LLM_MODE=mock/live/auto` 三态；LLM 层抽象出统一 `chat/embed` 接口并实现 `MockClient`；实现 M2 清洗服务。

- **背景**：配置的火山方舟 key 经多次组合验证均返回服务器明文 `AuthenticationError`（无效），真实 LLM 不可用，但不愿阻塞开发。

- **备选方案**：A）等新 key 再开发；B）临时硬编码假数据；C）Provider 抽象 + Mock。

- **选择理由**：C 能立刻推进 M3\~M7 开发/测试/演示、CI 零凭据可跑，且真实 key 到位后切 `LLM_MODE=live` 零改动——顺带把"外部依赖隔离"变成面试展示点。

- **后果**：管线现在无凭据可端到端演示；换 key/换厂商只改 `.env`。
